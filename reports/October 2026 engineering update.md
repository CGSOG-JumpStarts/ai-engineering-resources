# Keep specifications useful as agents evolve

**Research checkpoint: October 21, 2026.** This package benefits most from clearer engineering decisions around its existing examples. Beginners need to know how much specification a change needs, which files remain authoritative after a long session, and what evidence establishes completion. Frameworks can help organize that work, while repository permissions, backend checks and reviewers enforce its boundaries. The October update therefore deepens the current guides rather than adding another workflow to adopt. It retains the synthetic, deterministic lab and keeps live model, MCP and Foundry qualification separate from local tests. Product and release observations below reflect public pages inspected on this date; they are not installation or tenant-validation results.

## Match the workflow to the unresolved decision

Spec Kit now documents separate feature, defect-repair and idea-assessment paths. Its public release listing showed **v1.2.2**, dated October 19. BMad's installation page still described **v6.12 as stable and v7 as preview alpha**, despite retaining an earlier October 16 ETA; its release list showed v6.12.4 as Latest. An elapsed ETA cannot establish a release status. Keep the installed release, selected integration and extensions in the experiment record. ([Spec Kit](https://github.com/github/spec-kit), [Spec Kit releases](https://github.com/github/spec-kit/releases), [BMad installation](https://docs.bmad-method.org/start/install-bmad/), [BMad releases](https://github.com/bmad-code-org/BMAD-METHOD/releases))

This repository recommends sizing artifacts to uncertainty and risk. An isolated correction with known behavior can use a bounded task and focused regression check. A new permission boundary needs explicit actors, allowed data, denial behavior and integration evidence. Research should answer a named gap rather than repeat an adequate code inventory. HVE's October 16 RPI guidance supports selective research and distinguishes completed execution from accepted results. ([HVE RPI](https://raw.githubusercontent.com/microsoft/hve-core/main/docs/rpi/README.md))

The practical addition is a preservation list for brownfield changes: public schemas, authorization, error behavior and rollout constraints, each linked to current source and tests. Choose whether each specification is a historical record or a maintained contract. Spec Kit explicitly leaves artifact-maintenance conventions to the team. If the lab starts answering coverage guarantees contrary to AC-004, record a defect; code does not decide the intended policy. ([Spec maintenance](https://github.github.io/spec-kit/guides/evolving-specs.html))

## Preserve agreements outside compressed context

Agent Skills separates discovery metadata, activated instructions and supporting resources. That format helps organize reusable procedures; host compatibility and permissions still require verification. The guide now assigns stable conventions to repository instructions, agreed behavior to specs, current scope to tasks and repeatable procedures to skills. A small task context packet points to the approved revision, interfaces, tests, unresolved decisions and permitted actions. ([Agent Skills specification](https://agentskills.io/specification))

**A session summary is a navigation aid, not the authoritative agreement.** Compaction can discard details that become relevant later. Keep the approved spec and execution evidence in durable files and reopen them after resuming. A long session history, a retained audit log and the model's current context are different records. ([Context engineering](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents))

The update also separates removing irrelevant context, caching prompt prefixes and caching tool results. Cache counters and billing definitions are provider-specific; retain native categories before calculating comparable totals. Scope result caches by identity, permission and freshness. Set execution limits and truthful incomplete outcomes before a tool loop runs. These are proposed engineering practices, with no measured token saving claimed. ([Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching))

## Evaluate the resulting state and the authorized path

A convincing response can conceal an absent backend change, an unauthorized read or an unsafe retry. The evaluation guide now asks for independent evidence of intended state, permitted execution and truthful reporting. For a fictional case-creation workflow, that means one correct backend case, valid caller/approval evidence, and a response that agrees with the result. Exact call order matters only when the contract requires it.

Anthropic's January 2026 guidance distinguishes trial, trajectory and outcome and recommends repeated trials plus human calibration of subjective graders. First-attempt success, eventual success after retries and repeatable success answer different questions. Retain failed attempts and their costs; a best-of-several demonstration does not establish reliability. ([Agent evaluation guidance](https://www.anthropic.com/research/demystifying-evals-for-ai-agents))

The repository's fabricated trace scorer remains useful for teaching exact comparison and blocking security failures. It cannot observe real backend effects, prove protocol conformance or rank models. A real benchmark needs approved execution traces, appropriately scoped state assertions and a holdout set. A correct denial counts as success when denial is the required behavior.

## Specify recovery and identity before deployment

Foundry hosting documentation separates infrastructure ownership from client protocol and labels Hosted Agents GA while some Python integration packages remain prerelease. Choose execution behavior first: a known rule, a bounded model task, a tool-selecting agent loop or an explicit workflow. Hosting and protocol follow the application's operational requirements. ([Hosting choices](https://learn.microsoft.com/en-us/agent-framework/hosting/), [Foundry integration](https://learn.microsoft.com/en-us/agent-framework/hosting/foundry-hosted-agent))

The identity guides currently describe legacy Agent Applications alongside a newer agent object model. Their identity-creation and publishing behavior differs. Record the actual resource/API path and downstream role bindings, especially after migration. Foundry Skills and private catalogs remain preview at inspection; version promotion needs behavioral regression and rollback planning. ([Identity migration](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/migrate-agent-applications), [Skills](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/tools/skills), [Private catalog](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/private-skill-catalog))

Persisted conversation or session files do not establish whether a timed-out business write committed. Reconcile backend state before retrying and bind approvals to the verified actor and operation. Likewise, configured OAuth identity passthrough does not permit forwarding an arbitrary API token to an MCP endpoint. Validate token audience and backend entitlements independently. These checks belong in the integration contract and tests, even when the agent's answer looks correct. ([MCP authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization), [Foundry MCP authentication](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/mcp-authentication))
